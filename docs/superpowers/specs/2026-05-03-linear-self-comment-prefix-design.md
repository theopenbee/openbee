# Linear self-comment identification via body prefix

Date: 2026-05-03
Component: `internal/platform/linear`

## Background

The Linear receiver polls Linear's GraphQL API for new issue comments and
dispatches them as inbound messages. Without filtering, the bot's own replies
would be re-ingested on the next poll and processed as if they were user input.

Today the bot avoids this by recording each outbound comment's ID in
`~/.openbee/.linear/self_comments.log` (an append-only file loaded into an
in-memory set) and skipping any inbound comment whose ID is in that set. The
mechanism was introduced in `4f81383 feat(linear): persist self-comment IDs to
append-only log`.

## Problem

The ID-based filter has narrow failure modes:

- Persistence can fail between `commentCreate` returning and the bot writing the
  ID to disk (process crash, full disk, transient I/O error).
- The state file can be lost or moved (machine swap, container without volume
  mount, accidental deletion).
- Restarting on a fresh machine that shares the same Linear API key replays the
  bot's own historical comments as user input until the cursor advances past
  them.

Each of these is rare in isolation, but the failure mode — silently echoing a
bot reply back into the agent — is bad enough that we want a second, stateless
guarantee.

## Decision

Replace the ID-log mechanism with an explicit body prefix. Every outbound
comment is prepended with the literal string:

```
[openbee-bot]

```

(that is, `[openbee-bot]` followed by a blank line, then the original
message body). The receiver skips any inbound comment whose body starts with
`[openbee-bot]`.

The prefix is the **sole** mechanism: the existing `self_comments.log` file and
its supporting code are removed.

### Why this prefix

- Visible plain text — chosen over hidden HTML comments or zero-width markers
  for transparency and ease of debugging. Users can see at a glance which
  comments came from the bot.
- `[openbee-bot]` rather than `from:openbee` — vanishingly small chance a real
  user happens to start a comment with the exact tagged form.
- `strings.HasPrefix` match (not `Contains`) — a user quoting the bot's output
  in a reply will not accidentally suppress their own comment, because their
  text precedes the quoted prefix.
- Hardcoded as a `const` in `handler.go` — no configuration knob (YAGNI). If we
  ever need to change it, it is a one-line edit.

### Why drop the ID log entirely

- The prefix is generated by the same process that sends the comment, so as
  long as `commentCreate` succeeds with a prefixed body, the receiver can
  recognise it on the next poll without any persisted state.
- Maintaining both mechanisms doubles the surface area (two lookups, two
  invariants, two test paths) for a marginal robustness gain.
- The migration risk window is small and bounded (see below) and accepted.

## Scope

In scope:
- `internal/platform/linear/handler.go`: prefix injection in
  `LinearSender.Send`, prefix-based skip in `LinearReceiver.tickOnce`, removal
  of `selfComments` and all its plumbing.
- `internal/platform/linear/handler_test.go`: drop tests covering the ID log,
  add tests covering prefix injection and prefix-based skip.

Out of scope:
- The `platform.Platform` / `PlatformSenderAdapter` interfaces — unchanged.
- Cursor persistence (`cursor.json`) — unchanged.
- Issue ingestion path — unchanged (the bot does not create issues).
- Configuration system — no new config keys.
- A migration script for existing `self_comments.log` files — left in place,
  ignored, harmless.

## Design

### Constant

```go
const selfMarker = "[openbee-bot]\n\n"
```

`selfMarker` is the full prefix used when sending. Detection uses the bare tag
`"[openbee-bot]"` so that a body shaped like `[openbee-bot]\n<body>` (single
newline, e.g. via a future code path) is still recognised.

### Sender

`LinearSender.Send` prepends `selfMarker` to `msg.Content` before calling
`client.CreateComment`. The retry wrapper is unchanged. The post-send
`s.self.Add(c.ID)` callback is removed.

### Receiver

`LinearReceiver.tickOnce` replaces the `r.self.Has(c.ID)` check with
`strings.HasPrefix(c.Body, "[openbee-bot]")`. All other cursor and high-water
logic is untouched — a skipped self-comment still advances `highWater` based on
its `CreatedAt`, which preserves the existing forward-progress invariant.

### Removals

From `handler.go`:
- The entire `selfComments` struct, its constructor `newSelfComments`, and its
  `Add` / `Has` methods.
- `selfComments`-related fields on `LinearReceiver` and `LinearSender`.
- The `newSelfComments(dir)` call in `NewPlatform`.
- Any imports left unused after the deletion (`sync`, `errors`, parts of
  `os`/`path/filepath`/`strings`).

`strings` remains imported for `HasPrefix`.

### Tests

Remove:
- Cases that exercise `self_comments.log` file I/O, in-memory set hydration on
  restart, and ID-set skip.

Add:
- Sender writes `[openbee-bot]\n\n` followed by the caller's content to the
  underlying `CreateComment` mock.
- Receiver skips a polled comment whose body starts with `[openbee-bot]`.
- Receiver dispatches a polled comment whose body **contains** `[openbee-bot]`
  mid-string but does not start with it.
- Receiver still advances the cursor past a skipped self-comment.

## Migration

When the new code is deployed:

- Outbound comments sent under the previous version that have **not yet been
  observed** by the receiver (i.e., their `CreatedAt` is later than the cursor
  high-water mark at upgrade time) lack the prefix and are no longer in any
  consulted state file. They will be dispatched once as if they were user
  input.
- The window is bounded by the time between the last successful poll and the
  upgrade — typically less than `pollInterval` — and the impact is at most one
  duplicated inbound per affected comment.
- The existing `~/.openbee/.linear/self_comments.log` files are left on disk.
  They are harmless; users may delete them manually if desired.

This trade-off is explicitly accepted in exchange for the smaller, simpler
codebase.

## Risks

- **Tag collision.** A user begins a real comment with `[openbee-bot]` and is
  silently dropped. Probability is very low; mitigation is the prefix-only
  match (so quoted text is safe). If it ever occurs, the operator can spot it
  in Linear and we can change the marker.
- **Body rewriting by Linear integrations.** Some Linear apps may modify
  comment bodies. If an integration strips or alters the prefix, the bot would
  re-ingest the comment. No such integration is known today; the failure mode
  is observable (bot replying to itself in a loop) and bounded by issue label.

## Acceptance criteria

- All Linear-bound outbound comments observed in Linear UI begin with a
  `[openbee-bot]` line followed by a blank line, then the agent's reply.
- A bot-authored comment polled back from Linear is not dispatched as an
  inbound message.
- A user-authored comment that quotes a bot reply is dispatched normally.
- `internal/platform/linear/handler.go` no longer references `selfComments`,
  `newSelfComments`, or `self_comments.log`.
- `go test ./internal/platform/linear/...` passes.
