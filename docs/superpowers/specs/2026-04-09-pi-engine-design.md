# Pi Engine Integration Design

**Date:** 2026-04-09  
**Branch:** feat/engine-plugin  
**Status:** Approved

---

## Overview

This document describes the design for integrating **pi agent** as a new engine in the openbee system, alongside the existing Claude and Codex engines.

Pi is an AI agent CLI that follows the AGENTS.md specification (same as Codex). Its key difference from Claude and Codex is in session management: instead of capturing a session ID from the output stream, pi uses a pre-specified JSONL file path to persist and resume conversation history.

**Pi non-interactive command:**
```
pi --mode json --session /path/to/session.jsonl -p "prompt"
```
- `--mode json` and `-p` are required
- `--session` enables conversation continuity across runs

---

## Architecture

### Package Structure

New package `internal/ai/pi/`, mirroring the Codex structure:

```
internal/ai/pi/
├── adapter.go     # Implements EngineAdapter; registers "pi" in init()
├── invoker.go     # Subprocess management: command building, env injection, output monitoring
└── agentsmd.go    # Workspace file management (AGENTS.md + .openbee.md)
```

### Integration Points (zero interface changes)

- `adapter.go` calls `ai.Register("pi", factory)` in `init()`
- `app.go` adds `import _ "github.com/theopenbee/openbee/internal/ai/pi"`
- `EngineAdapter` interface is unchanged
- `session_store` is unchanged (stores path string instead of thread ID — same type)

### Config Struct

```go
type PiConfig struct {
    Path    string            // pi executable path, default "pi"
    Timeout time.Duration
    Env     map[string]string // Optional AI provider env vars (only injected if set)
}
```

Add `Pi PiConfig` field to `BeeConfig`.

### YAML Example

```yaml
bee:
  engine: "pi"
  pi:
    path: "pi"
    timeout: 30m
    env:
      ANTHROPIC_API_KEY: "sk-..."
      OPENAI_API_KEY: "sk-..."
```

## Session Management

### Key Design Difference

| Engine | Session ID Source | When Emitted |
|--------|------------------|--------------|
| Codex  | Parsed from `thread.started` event in output stream | After process starts |
| pi     | Generated by openbee before process starts | Before process starts |

### Session File Path

```
~/.openbee/.pi/sessions/<agentID>_<sessionKey>.jsonl
```

The path string itself is stored as the "sessionID" in `session_store` (no schema change needed).

> **Note:** `agentID` and `sessionKey` must be sanitized before use in filenames (replace any characters outside `[a-zA-Z0-9_-]` with `_`) to avoid path issues.

### Lifecycle

**First run** (no session in store):
1. Query `session_store(sessionKey, agentID, "pi")` → no record
2. Generate path: `~/.openbee/.pi/sessions/<agentID>_<sessionKey>.jsonl`
3. `os.MkdirAll` to ensure directory exists
4. Emit `OutputSessionID` with the path immediately (before process starts)
5. Launch: `pi --mode json --session <path> -p "<prompt>"`
6. `session_store` saves the path on completion

**Subsequent runs** (session exists):
1. Query `session_store` → retrieve path
2. File already contains history; pi reads and continues conversation
3. Emit `OutputSessionID` immediately (path unchanged)
4. Launch pi with same `--session <path>`

## Command Invocation

### Command

```
pi --mode json --session <sessionFilePath> -p "<prompt>"
```

### Environment Variables (three-layer injection)

1. **Base env** — `BuildBaseEnv(openbeeURL)`: prepends executable dir to PATH, sets `OPENBEE_URL`
2. **Openbee auth** — `OPENBEE_API_KEY` (always injected, for openbee MCP authentication)
3. **AI provider keys** — iterate `PiConfig.Env`, inject only keys with non-empty values

### Process I/O

- stdout → `logPath` (`O_CREATE|O_WRONLY|O_TRUNC`)
- stderr → `logPath` (merged, for debugging)

### Monitoring Goroutine

Waits for process exit only (no stream scanning for session ID):
- Exit code 0 → emit `OutputDone`
- Exit code non-0 → emit `OutputError`

## Output Parsing

### ExtractResult(logPath string)

Scans `logPath` in **reverse** (from file end) for the last `agent_end` event, returning immediately on first match for efficiency.

**Event structure:**
```json
{
  "type": "agent_end",
  "messages": [
    {
      "role": "assistant",
      "content": [
        {"type": "text", "text": "final reply"},
        ...
      ]
    }
  ]
}
```

**Extraction logic:**
1. Read file from end, scan backward line by line
2. Parse each line as JSON; skip lines where `type != "agent_end"`
3. On match: find the last `role=assistant` message in `messages`
4. From its `content` array, find the item where `type=text`; return its `text` field

**Comparison with Codex:**

| | Codex | pi |
|--|-------|-----|
| Event type | `item.completed` | `agent_end` |
| Result field | `item.text` | `messages[-1].content[type=text].text` |
| Scan direction | Reverse | Reverse |

## Workspace Setup

### SetupWorkspace(workDir, role, opts)

Follows the Codex pattern (pi follows AGENTS.md spec):

1. **`AGENTS.md`** — role persona file, created with `CreateFileOnce` (idempotent)
2. **`.openbee.md`** — system rules, always overwritten to stay current
   - Bee role → `BeeRules()`
   - Worker role → `WorkerRules()`

`agentsmd.go` can be largely copied from `internal/ai/codex/agentsmd.go` with pi-specific persona content.
